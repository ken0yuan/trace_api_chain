# 三阶段独立流水线

测试采集、离线整理、最终写库是三条同时推进的生产线。采集只把自己的结果落盘；整理消费已经结束的测试结果；写库消费已经整理好的完整贡献。CPU 整理和后面的 NPU 测试可以同时运行。

| 阶段 | 并行数量 | 输入与输出 |
|---|---:|---|
| 采集 | 8，0～7 每卡一个任务 | 同时启用 trace-api-chain 和 test-api，每例独立原始记录 |
| 离线整理 | 8 | 只读公共源码/编译库与本例记录，生成本例完整入库贡献 |
| 最终写库 | 1 | 串行提交调用链库和 API 对照库，核验后清理本例中间产物 |

trace-api-chain 候选版本为 0.3.3，test-api 保持 0.1.10。PyTorch、torch-npu、编译符号、LLD 和只排除官方 C++ 标准库头文件的既有编译条件不变。完整台账仍为 10,362 项；不按相关性或重要性去掉对象。

## 采集不等待后面的阶段

旧适配器把整理和写库合在一个串行消费者中，结果队列最多放 8 项；队列一满，采集工作线程就阻塞在入队。现在采集只持久化独立结果并提交一个路径；后续堆积不会阻塞采集。已有用户停止指令和磁盘资源保护仍有效。

整理最多同时处理 8 例，待写的整理贡献有容量限制，这个限制仅约束整理端的派生数据，绝不占住采集线程。写库收到哪份整理完成的结果，就处理哪份，不被较早但尚未整理完的用例卡住。停止后，已落盘的结果可继续消费，已完成测试不会重跑。

## 没有跨测试的可写整理缓存

之前共用的是 ELF 地址到源码位置的缓存，不是测试结果之间存在数据依赖。新流水线取消这个共享可写缓存：每例有独立整理目录、独立符号缓存和完整入库文件。公共源码、编译库和 API 台账是只读输入。

原始采集字节保持不变。整理工作区通过同例原始文件的硬链接读取输入，避免复制一遍大文件；派生图、解析缓存和入库贡献只写入本例工作区。不同测试不共用这些可写文件。无法安全绑定到本例的外部输入链接会被拒绝。

## 写库后清理

整理进程不打开数据库。它把实体、完整路径、对象引用、源码依赖、未解析对象说明全部放进有 SHA 绑定的交接文件；最终写库阶段验证交接文件、原始输入和图摘要后执行事务，保留原有原子提交和外键校验。

先提交调用链库，再提交并核验 API 对照库。两边都成功后，核对图 SHA、目标槽位状态、API 原始映射验证记录、完整测试阶段及本次采集批次，先原子保存精简完成凭据，再删除该例原始事件、原生路径文件、临时运行时、派生图、解析缓存、入库交接文件、pytest 中间日志和 JUnit 文件。最终数据库、完成凭据和流水线运行记录保留。

任一提交/核验失败不删除中间数据。清理中断后可依据已持久化的提交凭据继续清理，不重新采集、整理或写库。测试失败的必要诊断先写入最终记录。尚未验证入库的 fork 子分支必须保留，不能把新实体当成中间垃圾删除。

两个插件的测试名字存在明确的存储格式差异：test-api 使用 `pytorch/` 仓库前缀。核验只接受这个精确路径映射，要求本次 source_attempt 相符；同名歧义、其他批次或阶段不完整都会拒绝删除，不按函数名后缀猜测。
