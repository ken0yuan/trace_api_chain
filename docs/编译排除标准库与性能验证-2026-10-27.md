# 仅排除官方 C++ 标准库头文件：构建、性能与调用链验证

日期：2026-10-27（Asia/Shanghai）

## 结论

CPU fill_ 原始完整测试：默认 679.509 ms，全插桩 21603.880 ms，仅排除标准库 6712.795 ms。
新版本比全插桩版减少 68.93% 的耗时，仍为默认版的 9.88 倍。

## 一、精确范围

新增的唯一插桩排除选项：
`-finstrument-functions-exclude-file-list=/usr/include/c++/11/,/usr/include/aarch64-linux-gnu/c++/11/`
保留 -finstrument-functions 和 -g1；仍使用 GCC 11.4 和 LLD 22.1.8。
插桩是在函数进入、退出时各增加一次报告调用。即使没有启用采集插件，编译进库里的这些额外调用仍要执行；调用次数很多时会拖慢测试。-g1 用于保留基本源码调试信息，LLD 负责把编译产物链接成库。
按函数定义所在的绝对文件路径匹配，不按 std:: 名称匹配，也不排除整个 include 或 third_party。
PyTorch、torch-npu、ATen、c10、op-plugin、pybind11、Python 头文件、fmt/JSON 等其他依赖均未加入排除列表。
GCC 目录中的 11 是编译器版本，项目编译语言标准仍为 C++20。
此前排除 std+pybind11 的 r8 尝试已按用户要求中止，未作为结果或对照；本次 r9 使用另一份干净源码及独立环境。

## 六、真正排除了什么，保留了什么


独立计数进程只累计函数进入/退出次数，不写逐次事件；它与所有性能计时分开执行。下面是单次 10000 元素 float32 操作的进入次数，每次进入还对应一次退出。

| 操作 | 全插桩进入数 | 仅排除标准库进入数 | 全插桩中官方 C++ 头文件进入数 | 新版官方 C++ 头文件进入数 |
|---|---:|---:|---:|---:|
| fill_ | 39,384 | 13,799 | 25,585 | 0 |
| tensor_from_list | 352,743 | 351,394 | 1,342 | 0 |
| isclose | 5,893,149 | 969,428 | 4,923,723 | 0 |

文件归属按实际解析到的定义路径判断，而非函数名是否含 std::。未解析到源码的函数单列 unresolved，不能把未解析说成已确认属于某个库。
新版 tensor_from_list 中仍存在 pybind11 和 Python 头文件函数记录，fill_/isclose 中仍存在 PyTorch 自定义函数记录。完整分类及源码明细在 validation JSON 中。

## 七、调用链验证


全部 22 个实例使用同一份 10362 项 API 清单进行紧凑路径采集与重放，无采集缺口。功能通过 17、已知失败 5；数据库完整性及外键检查通过。
此前全插桩采集中已观察的 API 别名均保留：True。
22 份记录合计：原生路径 45.86 MB，Python 记录 102.26 MB，SQLite 数据库 470.21 MB。
已映射的 C++ 源码对象中，PyTorch 2109 个，torch-npu 295 个；全部语言的映射/未解析统计保留在调用链摘要中。
C++ 标准库节点是按用户明确范围省略的；链路只对其余已插桩且实际执行的主机代码负责，不能称为包含所有库、所有线程和设备内核的完整执行历史。紧凑模式保留路径、分支和计数，不保留每次调用的时序；源码无法确定的对象仍标为未解析。
函数节点复用减少记录与存储；本轮编译排除则直接减少要执行的钩子，两者是不同层面的改进。

## 九、这次发现并修复的插件兼容性问题


第一次新版 CPU fill 采集失败，测试计算通过。native-paths.bin 的失败位为 96（32：返回校验不匹配；64：未闭合栈）。回执里的 14338 是采集段序号，不是失败位或文件大小。失败目录 captures/ 及诊断目录 diagnostic-capture/ 均保留。
实际机器指令确认：GCC 将 ATen 的 Vectorized<c10::BFloat16>::store() 部分内联，又生成 .part.0.isra.0 辅助函数。进入钩子位于外层 vectorized_loop，退出钩子位于拆分出的辅助函数，两次 this_fn 相同但 call_site 不同。
旧插件把 call_site 也当作入口/出口配对的强制条件，因而误报。修复只按当前线程栈顶的函数地址和窗口配对；不搜索或跳过栈帧。调用位置仍以入口值标记路径，出口位置变化另行计数（windows.json 的 exit_callsite_variations；graph.json 中也标明）。原始事件模式还保留不同的 exit_caller_address。
函数不匹配、跨窗口返回、缺入口、缺出口仍报错；递归仍保留各栈位置。新增回归覆盖这些条件，完整插件测试 82 项通过。修复后的正式结果位于 captures-v2/，没有覆盖失败证据。
性能计时在修复前已经完成，全部关闭插件，因此性能表不包含此采集器改动的收益。
官方插桩选项文档：https://gcc.gnu.org/onlinedocs/gcc-11.1.0/gcc/Instrumentation-Options.html
