# 0.3.2：无结果、采集不完整与错误 API 入口修复

本文面向使用者：不需要理解编译器，就能区分测试计算、采集、关系合并和图回放的问题。服务器仍是 `179.163.3.2` 的免密容器，工作根目录 `/home/workspace-ycy`。

## 先区分四件事

- pytest 通过：测试自身的断言通过。
- 采集完整：选定测试函数确实开始并结束，声明范围内的调用、返回和对象引用没有采集缺口。
- 关系合并成功：API ↔ 测试证据经过核对写入关系库，随后删除本次关系中间分片。
- 图回放成功：原始调用证据经过栈、窗口、计数和来源校验后写入调用链数据库。

任何一项都不能替代其他项。旧版有些测试通过，但 profiler 替换了采集回调，因此链路不完整；另一些测试在采集器反复遍历大对象时超时，连 pytest 的最终结果也没有。

## 找到的原因和对应修复

### 1. 不同 Python 函数共用代码，不代表它们是同一个 API

`contextmanager` 等包装器可以让不同函数拥有相同的字节码和全局变量。旧匹配方式会把不相关的包装器误认成台账 API。现在通过 CPython 3.11 的实际执行帧读取精确函数对象，并检查方法接收对象的真实继承关系。不会调用用户类的 `__instancecheck__` 或 `__subclasscheck__` 来猜测所属关系。

### 2. 普通 list.append 不是 EventList.append

PyTorch 的 `EventList` 继承 `list`，两者共享同一个底层 append 方法定义。只有方法定义相同、实际接收对象也属于台账声明的类，才能算对应 API。普通列表上的 append 不再产生 EventList 的 API 根；真正的 EventList、它的子类以及事先保存的绑定方法仍然识别。静态方法、类方法和不使用 self 作为参数名的方法也分别验证。

这不是删掉 Python 标准库或 PyTorch 对象：真正 API 调用下面实际发生的子调用仍然保留。修的是错误的入口归属。

### 3. 采集器会从 pytest 对象绕回自己的证据缓存

对象引用可以经过 pytest 的配置、插件管理器或闭包，回到采集器本身。继续递归会把正在增长的证据又采成新证据，造成大量无效工作。

现在只对精确登记的采集器、原生桥、台账和关系观察器设置边界：保留指向这些对象的引用，停止枚举它们的内部采集状态。没有按模块名筛除 PyTorch、torch-npu、pybind11、Python 头文件或自定义 C++ 库。

### 4. profiler 改回调后，下一条指令再恢复已经太晚

Torch profiler、cProfile 和 Python 的 setprofile/settrace 会调整解释器回调。旧方式等下一条 Python 指令才恢复，会漏掉切换这次 C 调用的真实返回。

关系插件 0.1.10 提供独立的观察通道，并保护确切的原生切换入口。在原生函数真正返回解释器前恢复观察器，继续转发测试自己的 profiler/trace 客户端。原生 callable 的对象身份、参数、结果和异常保持；调用链使用原始原生函数地址。事先保存的 setprofile/settrace 同样覆盖。未知入口绕过保护时仍报告缺口，不生成假的调用或返回。

这里没有使用 LD_PRELOAD 替换解释器的 setter：本机独立 CPython 可执行文件会优先绑定自己的符号，该实验已经否定。LD_PRELOAD 继续只承担已验证的编译插桩采集。

原生 hook 在观察器回调期间进入线程局部的静默区，避免观察器自己调用 Torch 编译控制接口时产生的事件混进真实 API 窗口。静默区嵌套经过测试，真实递归深度仍保留。

### 5. fork 子进程可能继承永远不会结束的“正在导入”状态

Kineto 测试的 torch-npu 后台监控进程在父进程导入 torch 的中途派生。它继承了模块的 `_initializing` 标记，而父进程剩余的导入不会在该子进程执行。旧采集器一直等标记消失，因此缺少子进程最终回执。

对这种明确经过 fork 传播的上下文，关系插件使用已经存在的 torch 模块绑定启动观察，不在子进程重新执行父进程的导入。之后的绑定增加、修改仍由版本检查发现。普通 spawn 和正常导入的等待策略保留。这不是把后台进程加入忽略名单。

### 6. 首次 forward AD 会加载很大的分解注册表

首次 make_dual 会加载 JIT 分解。采集器若在每一行重新遍历全部注册表和源码字符串，少量算子也可能变成很慢的测试。

现在按每个引用根验证和复用状态：列表和元组逐项检查对象身份；嵌套容器、字典版本、闭包、默认参数、实例字典和受支持的槽位由 CPython 适配器检查。验证用完整字节序列比较，不靠哈希碰撞概率判断相同。只复用完全一致的引用结果；不支持安全验证的存储继续使用普通观察。缓存只持有观察记录，不长期持有工作负载对象。预算耗尽仍明确标记为不完整。

每个源码对象仍然存在。多次调用及递归路径不会因为复用对象而变短。回归将缓存开、关两种方式产生的引用增删逐项比较，包含别名、循环、替换元素、追加元素、嵌套修改、闭包变化和类名变化。

### C 层字段与 Python 临时包装对象要区分

例如 `_io.FileIO._blksize` 在 C 结构体内是一个数值字段，每次读取都可能新建一个 Python 整数包装。两条引用路径读到同一个字段，却得到不同包装地址；这不等于字段内保存了两个不同对象。旧逻辑把它当成同次观察中状态不一致。

现在，对 `PyMemberDef` 明确声明的非对象字段，保留一个 `storage_member` 节点，记录所属对象、声明类、字段名、字节偏移和 C 字段类型。不会凭空制造一个“存储的 Python 整数对象”。`T_OBJECT` 与 `T_OBJECT_EX` 仍使用真正存储的 Python 对象身份；真实别名、数组元素、槽位对象和引用变化仍保留。

同次观察内，一个共享对象只读取一次，其他引用根复用它已经观察到的邻接状态。跨次观察前仍验证状态；对象元信息也验证类型、源码所属模块和确切 callable 的变化。缓存采用 128 MiB 的估算容量上限和 4,096 项上限，淘汰只影响耗时，不影响必须观察到的结果。验证包括缓存开关对照、字段节点保留、嵌套修改和缓存淘汰。

### Python 运算符也可能直接进入 C++

只观察 `c_call` 会漏掉 `a + b` 等通过类型槽进入的 C++。新录制在实际的 Python 帧边界和 `c_call` 边界都开启原生窗口；原始输入必须声明 `python-and-c-boundaries/1` 策略，回放才接受这种归属。没有据函数名补造跨语言跳转；仍检查进程、线程、时间包含和真实原生进入/返回平衡。

### 7. 关系分片清理不能删掉图回放所需的二进制

双插件运行时，关系观察器的源码和本机 C 适配器放在调用链证据下的 `observer-runtime/`。关系原始分片照常核对、合并、删除；图确实依赖的这些运行时文件作为可复现输入保留，并进入回放原始文件哈希清单。这样不会先删除符号解析要读的文件，再把缺失来源当作完整图。

单独运行关系插件时，仍采用原来的关系临时目录布局。

## 只消除可证明的重复，不筛除新实体

用户的明确要求是：可证明相同的实体、引用状态、下一跳和路径才复用。新实体、新关系和新分支全部保留；不能确认相同的分别记录。没有按“看起来无关”或“重要程度”去掉对象，没有增加 PyTorch、torch-npu、pybind11、Python 头文件的筛除。

- `shared-adjacency-states/1` 把同一对象的确切邻接状态定义一次，每次调用仍保存其状态关联与增删。回放验证对象、状态、父对象与真实删除操作，数据库与旧逐边记录的输出对照一致。
- 根对象改变时，只复用经过完整签名重新验证的既有内部状态，不据地址相等推断生命周期或状态相等。共享别名边保留，共享后代不重复计入预算。
- 类自身签名不受支持时禁用元信息缓存，避免改名后继续返回旧说明。
- 外来槽位描述符的声明类先与实例实际类型核对，防止按错误布局读内存；对象仍保留。描述符不能用于该实例时如实记录读取边界。

## 路径容量与超时属于明确的资源边界

日志张量原始用例在 1,000,000 个原生路径节点处耗尽容量；原始文件头的失败位为 68，即节点容量位 4 和随后未收束的栈位 64，并不是函数/窗口不匹配位 32。新插件报告 `native_path_node_budget_exceeded` 等具体原因，不再让后续“无法开启窗口”异常掩盖首因。耗尽后的结果保持不完整，不制造返回事件。

本轮将复测和恢复批次的路径预算设为 4,000,000。每卡仅原生节点和节点哈希的上限约 128 MiB，另有原有支持记录预算；主机实际内存充足。增加容量没有去掉任何新路径，也未改变编译选项。

`test_fractional_max_pool3d_npu` 曾由内部 1,800 秒超时终止，没有 pytest 最终回执；已有采集文件和 CPU fallback 日志证明不能将它解释成“未进入测试”。针对这个已知用例的后续预算为 7,200 秒，保留全部实体与调用。调度记录区分内层采集超时、外层调度超时，以及缺回执时未知的正文起止状态。

## 回放只缓存重复计算

源码内容只切行一次；同一源码实体的词法容器匹配和相同路径身份计算复用。证据覆盖顺序、源码身份公式、路径、引用、依赖与外键保持，回归对旧算法与新算法的全部 SQLite 表逐行比较。

首次冻结证据时，校验得到的完整图继续用于后续处理，取消原来第二次相同重建。共享引用视图按实际增删验证，调用返回后释放验证所需的活跃状态；历史观察仍完整保留在证据和图中。

真实整例对照在 `replay-benchmark-reviewed/`，用同一份已冻结证据、相同已暖符号缓存、两个独立数据库，依次执行旧版与新版。结果尚未完成时不得将局部微基准倍率当成整例加速。
