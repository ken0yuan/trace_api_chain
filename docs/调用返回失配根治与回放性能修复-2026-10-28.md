# 0.3.1：调用返回失配与离线回放性能修复

日期：2026-10-28。整理、实现及验证：Codex / OpenAI。

## 这次出了什么问题

八卡全量测试中，有 75 个卷积梯度检查用例本身通过，但调用链插件报告 `collector_error:TypeError` 和 `call_return_mismatch`。这些结果没有被算成完整调用链。

在同一机器上单独串行运行原用例，仍然出现相同异常。异常堆栈指向 `Registry.match()` 的 `issubclass(owner, cls)`：API 目录里有带数据成员的 Python Protocol，Python 不允许用 `issubclass()` 对它做这种检查。错误信息涉及 `_synchronize_after_execute` 和 `should_synchronize_after_execute`。

因此这次已确认的触发原因是插件执行了不适用的类型检查，并非必须八卡并行才会发生。它在记录函数入口之前抛异常，入口漏记，随后返回事件面对的却是父调用，因而又报告失配。

## 为什么不能只捕获这个 TypeError

采集器除了记账，还会观察局部变量、返回对象、API 别名和原生窗口。旧逻辑中，观察过程抛异常可能阻止正常的入栈、出栈或原生窗口处理。即使一个触发点修好，其他观察错误仍可能造成同类连锁失配。

0.3.1 做了两层修复：

1. API 方法归属按接收对象真实的 MRO 继承链匹配，逐项比较类身份；不执行结构协议检查，也不调用用户自定义的 `__subclasscheck__`。
2. 将可选观察与调用栈维护分开。API 匹配、源码定义观察、入口/出口/返回快照或原生窗口处理失败时，明确记录异常缺口；已匹配的真实返回仍然出栈，不让观察错误污染后续调用。C 返回还同时核对调用者帧与 callable 身份。

未知错误会保留异常阶段、参数类型/字符串及堆栈，便于以后直接定位。存在观察错误的结果仍然是不完整结果。真实不匹配的返回不会被忽略，也不会通过猜测父对象、任意弹栈或伪造返回来恢复成成功。

Python 抛异常、C 函数抛异常、生成器暂停与恢复的正常事件都属于回归覆盖。此前针对编译器优化导致入口/出口调用位置不同的 C++ 修复继续保留：函数、线程、窗口和真实栈顶仍然严格匹配。

每个真实用例都加载两个插件和完整的 10,362 个 API 清单，使用原来的 Python 3.11、带 `-g1` 和函数插桩的 PyTorch / torch-npu。没有缩小 API 范围、取消 Python/pybind11 插桩、忽略返回失配或放宽采集缺口标准。

“无缺口”指当前声明的采集范围通过校验，不代表其他线程、分布式子 rank、图编译内部、设备内核或所有 Python 堆对象都已完整枚举。无法证明源码归属的对象仍明确保留为 pending。

## 图回放为什么会越来越慢

回放先把原始数据解析成调用图，再把源码对象、路径和测试支持关系写入 SQLite。测量中，主要耗时在数据库刷新，而非地址解析。

一次细分测量里，检查旧源码记录是否需要标记为 stale 的关联查询执行了 402 次，累计耗时 209.12 秒。缺少从源码路径找到实体、再由实体找到测试支持记录的索引，导致反复扫描不断增长的历史数据。

新增三个索引：

- `entities_source_version(path, source_sha256)`：按源码文件和版本定位实体。
- `slot_entities_entity(entity_id, slot_id)`：按实体定位支持它的测试。
- `paths_parent(parent_id)`：删除无支持路径时，高效检查父子引用。

现有库会自动补索引。源码变更检测、事务回滚、证据保留与完整外键校验继续执行。

## 第一阶段：索引修复的等条件性能对照

两组使用同一份冻结采集、相同的起始 SQLite 快照、相同二进制和源码缓存；只改变回放实现。两组分别入库到独立副本，避免“第二次其实没有做入库”造成假提速。

| 阶段 | 修复前 | 修复后 |
|---|---:|---:|
| 离线准备与地址解析 | 6.282 秒 | 5.848 秒 |
| 数据库刷新 | 249.923 秒 | 28.240 秒 |
| 合计 | 256.204 秒 | 34.089 秒 |

该输入总耗时缩短约 86.7%，约快 7.52 倍。不是所有测试都会得到相同倍数；这是同一实际采集在约 2.6 GB 历史库上的对照。

前后图摘要完全一致；实体、路径、别名、依赖等表做了双向数据对照。`path_support` 和 `pending` 做了本次 slot 的完整双向对照，并核对全表行数。仅用于标识回放代码版本的 `import_digest` 预期不同；原始输入和图摘要一致。

## 第二阶段：约 20 GB 正式图的额外瓶颈

恢复时正式图已增长到约 20 GB，首批新用例的回放仍约需 241～269 秒。因此不能把前面约 2.6 GB 快照上的 7.52 倍提升直接用于当前大库。

从正式库取得一致性只读备份后，逐条计时查明：原路径清理查询按表中插入顺序扫描路径，反复随机查询整个历史支持索引；完整外键检查也会对数千万条关系做查找。仅把 SQLite 默认约 2 MiB 页缓存调到 256 MiB，总耗时只由 214.6 秒降至 198.6 秒，约快 8%，没有将它误报为明显提速。

最终改动仍检查全部历史路径，但先按源码路径身份索引顺序找出无支持记录，再按 rowid 删除同一批记录，避免随机访问。采用 rowid 保留了对空身份记录的原有清理语义；无支持的父子路径和空身份记录有专门回归。写入连接的页缓存预算设为 4096 MiB；通过 `--db-cache-mib` 可在 1～16384 MiB 之间调整。它按需使用主机内存，不预先占满，不占 NPU 显存，也不是整个进程的内存上限。这台机器约有 2 TiB 主机内存且只有一个入库线程，4 GiB 预算约占 0.2%。只读查询保留原设置。

再次从同一份已冻结、已有索引的 20.3 GB 数据库复制两个独立副本，使用同一采集、相同 slot 和相同源码/地址缓存，只改变清理 SQL 与写入页缓存预算：

| 阶段 | 优化前 | 优化后 |
|---|---:|---:|
| 离线准备 | 5.718 秒 | 5.618 秒 |
| 历史无支持路径清理 | 62.293 秒 | 9.182 秒 |
| 完整外键检查 | 128.119 秒 | 76.453 秒 |
| 数据库刷新合计（含上述两项） | 203.546 秒 | 97.086 秒 |
| 整体合计 | 209.264 秒 | 102.704 秒 |

整体约快 2.04 倍。图摘要和报告相同；全表行数相同，所有含 slot 的表逐条双向核对本次 slot，较小的全局表也做了全表双向核对。大型历史全局表核对行数，不声称对 20 GB 历史做了完整逐行双向比较。对照通过连接适配器施加与最终实现相同的 SQL 和缓存设置，以保留相同策略指纹；最终打包实现另经 107 项回归验证。

两组都实际执行新 slot 的事务导入与完整外键检查，没有利用重复导入的 unchanged 短路，没有省略校验或裁剪 API。操作系统页缓存未清空，正式流水线继续运行；这是单次配对诊断结果，不是独占机器上的重复统计实验。两阶段数据库和起始实现不同，提速倍数不能相乘。完整外键检查仍是当前主要开销，仍随历史库增长；这次没有取消或抽样它。证明见 `large-final-comparison.json` 及对应 SQL 计时。

## 如何恢复正式结果

原异常数据及停止前的两个数据库先保留备份。修复采集重新生成经过标准回放验证的独立数据库，再由一个写入进程分批事务合并到正式图；每个批次最终执行完整外键检查。这个维护过程可以并行解析，正式数据库仍只有一个写入者。

维护工具只接受无缺口、单一完整 slot、源码身份和版本一致的输入；拒绝覆盖已存在 slot、版本冲突和不完整输入。回归测试核对了它与逐次标准入库的全表等价性，并验证整批失败时回滚。

API 与测试关系插件的旧正确关系保留。重跑产生的新别名、调用位置及来源证据在核验后做单调追加，原有完成记录和旧证据不得减少。API 原始分片仍然在验证合并成功后清理，调用链原始采集的存储规则不变。
