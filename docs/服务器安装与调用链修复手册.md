记录日期：2026-10-26（北京时间）。适用插件：`trace_api_chain`，本次修改基线为 `96c5fbc4cec6611a7a248f030f6b787b893ef372`。

这份文档面向不熟悉底层编译的使用者：先说明如何使用已经装好的服务器环境，再说明如何重建，以及为什么这样修复。本文记录的是这次实际验证的版本与结果，不承诺其他版本、机器或 CANN 组合有相同表现。

## 1. 先理解我们装了什么

| 名称 | 可以怎样理解 | 本次用途 |
| --- | --- | --- |
| PyTorch（Python 包名 `torch`） | 提供 Tensor、神经网络等 API 的框架 | 被测试、被追踪的主体 |
| torch-npu（导入名 `torch_npu`） | 让 PyTorch 能调用昇腾 NPU 的适配层 | 连接 PyTorch 与 CANN |
| CANN 和驱动 | 操作 NPU 所需的厂商软件 | 这次沿用服务器已有环境，没有重新安装驱动 |
| venv | 一套独立的 Python 包目录 | 分开保存默认库、插桩库，防止相互覆盖 |
| GCC | 把 C/C++ 源码编成目标文件的编译器 | 本次为 11.4 |
| LLD | 把目标文件组合成共享库的链接器 | 本次为 22.1.8；没有把 GCC 改成 Clang |
| wheel（`.whl`） | Python 的安装包 | 安装编译完成的 torch-npu |
| `trace_api_chain` | 运行测试时收集调用关系，之后生成源码图的 pytest 插件 | 不是 PyTorch Profiler，也不是运行耗时计时器 |

Python 调用通常会继续进入 C++，再进入设备运行库。只看 Python 代码，不能看到其中全部主机函数。因此我们另外编译了带“插桩”的库。

- `-finstrument-functions`：编译器在函数进入、退出处插入通知。插件接到这些通知后记录调用路径。它会增加代码大小和运行成本。
- `-g1`：在产物中保留较少的调试信息，让离线工具把机器地址对应回源码。它不表示关闭优化；两组仍使用 Release / `-O3 -DNDEBUG`。
- `-fuse-ld=lld`：告诉 GCC 在链接时使用 LLD。
- `LD_PRELOAD`：让采集进程优先加载插件的通知接收器。插件自动设置，平时运行和性能计时不要手动保留它。

本次只比较 **默认构建** 与 **同时增加 `-finstrument-functions -g1` 的构建**，没有把两个选项拆成三组比较。

### 3.3 下载 PyTorch、torch-npu 和子模块

本次 PyTorch 从 ghfast 转发的 GitHub 仓库拉取，torch-npu 从 GitCode 拉取：

```text
https://ghfast.top/https://github.com/pytorch/pytorch.git
```

`R/sources/pytorch` 和 `R/sources/torch-npu` 已经准备好。复现前检查它们的 `git rev-parse HEAD` 是否与上表相同。首次从空目录准备时，可先 clone，然后 fetch 并 checkout 固定 commit；不要把将来的 main/master 当成本次版本。

```bash
# 仅用于尚不存在的源码目录；现有服务器不要重复 clone 到同一路径。
git clone --depth 1 --branch main https://ghfast.top/https://github.com/pytorch/pytorch.git "$R/sources/pytorch"
git -C "$R/sources/pytorch" fetch --depth 1 origin 26650ac257aee280144c73a51a99a1d7a43ee161
git -C "$R/sources/pytorch" checkout --detach FETCH_HEAD

git clone --depth 1 --branch master https://gitcode.com/Ascend/pytorch.git "$R/sources/torch-npu"
git -C "$R/sources/torch-npu" fetch --depth 1 origin fc51851eb378dc663d4798435110af75968ad3e3
git -C "$R/sources/torch-npu" checkout --detach FETCH_HEAD

git -c url.https://ghfast.top/https://github.com/.insteadOf=https://github.com/ \
  -C "$R/sources/pytorch" submodule update --init --recursive --jobs 8
git -c url.https://ghfast.top/https://github.com/.insteadOf=https://github.com/ \
  -C "$R/sources/torch-npu" submodule update --init --recursive --jobs 6
```

“子模块”就是主仓库另外引用的源码仓库。只下载主仓库 ZIP 或 wheel 并不等于拿到了完整构建源码。检查 `git submodule status --recursive`，前缀 `-` 表示尚未初始化，`+` 表示版本不一致。失败应先看下载日志、补齐对应源码，再开始计时。

还要注意 CMake 在构建时补拉的依赖。我们发现 NCCL 会在此时下载，因此把它提前准备到 `sources/pytorch/third_party/nccl`，固定为上表版本。状态记录见 [nccl-source.json](reproduction/2026-10-26/nccl-source.json)。网络下载不能混进编译耗时。DVM、TorchAir 等 torch-npu 默认组件没有为了缩短耗时而关闭。

### 3.4 准备 LLD 和离线解析工具

本次 LLD 来自 `apt.llvm.org` 的 Ubuntu Jammy ARM64 包，解压到 `R/toolchains/llvm22/root`，没有执行系统级链接器替换。`bin/ld.lld` 是包装入口，只给这个链接器设置所需的动态库搜索路径。

[lld22-manifest.json](reproduction/2026-10-26/lld22-manifest.json) 保存了下载来源、精确包版本、SHA256、附加依赖和链接器二进制 SHA256。复建时应使用这些固定包并核对校验值；在线仓库的最新元数据可能已经变化。

解压方式是 `dpkg-deb -x 包文件 目标目录`。需要 `libllvm22`、`lld-22` 及缺少的依赖；本次另外解压了 libedit2、libz3-4、libbsd0、libmd0。GCC 仍然使用系统 11.4。验证入口：

```bash
"$R/toolchains/llvm22/bin/ld.lld" --version
# 本次输出：Ubuntu LLD 22.1.8 (compatible with GNU linkers)
```

插件离线解析还需要 elfutils、libdw 和 libelf 的运行库/头文件。本次从 Ubuntu 包中独立解压了 elfutils、libdw-dev、libelf-dev、libdw1、libelf1、libasm1、libdebuginfod1，放在 `R/system-tools/root`。`environment/plugin-env.sh` 会设置可执行文件、头文件、链接库和运行库路径。

这些工具分别负责不同事情：**LLD 用于生成库；libdw / eu-addr2line 用于事后读库里的源码信息。** 看到 libdw 报错，不等于 PyTorch 编译错了。

### 3.5 一次构建并安装两组库

当前服务器的源码、基础环境、构建工具及准备状态都已齐全。实际编译脚本位于 `R/scripts/run_benchmark_lld.py`，仓库内备份见 [同名脚本](reproduction/2026-10-26/run_benchmark_lld.py)。

```bash
R=/home/workspace-ycy/compile-performance

  --attempt manual-20261026-a --linker lld --lld-layout native
```

`--attempt` 必须使用没有存在过的新名字。这会创建 `cases/baseline-名字` 和 `cases/instrumented-名字`。本次正式结果的名字是 `r7-lld22`；不要复用它。

该脚本是**当前工作区的构建驱动**，不是全新机器的一键安装器。它依赖 `sources/`、`venv311/`、`build-tools/`、LLD 及准备状态文件；源码准备状态缺失时会等待。新机器应完成前面各项准备，不能只复制这个脚本就开跑。128 个编译任务是本机 256 CPU / 大内存配置下的选择，换小机器要调整脚本中的 `JOBS`。

它依次完成：

1. 为两组分别复制纯源码和基础 venv，避免覆盖及复用目标文件。
2. 默认组不增加两个选项；插桩组同时增加它们。通过 GCC 包装器记录实际编译命令，并向嵌套构建传递选项；不能只设置一次 `CXXFLAGS` 就认为所有子项目都已覆盖。
3. 两组统一 GCC 11.4、LLD 22.1.8、128 编译并行、8 链接线程，使用 `CMAKE_LINKER_TYPE=LLD` 的原生布局和上游符号排序。
4. 在 PyTorch 源码目录执行 `python -m pip install -e . -v --no-build-isolation --no-deps --no-index`。这些选项使用已经准备好的构建依赖，不在计时中另建环境或下载依赖。
5. 将 PyTorch 的 Python 源码和已生成的原生安装树整理到该组 venv 的 `site-packages`。这是文件整理，不重新编译，也不计入编译时间。这样 torch-npu 能看到正常的 `include/lib/share` 布局，且不会误导入 PyTorch 的 `tools` 命名空间。
6. 在 torch-npu 源码目录执行 `bash ci/build.sh --python=3.11`；进入这一阶段前清除全局 `CMAKE_GENERATOR`，让 TorchAir 内部需要 Makefile 的步骤正常运行。
7. 把新生成的 `dist/torch_npu*.whl` 用该组 Python 的 `pip install --no-deps --no-index` 安装，检查包版本和导入情况。随后另外执行 CPU/NPU 运算与插件验证。

PyTorch 必须先安装，torch-npu 编译才能找到对应的头文件和库。普通预编译 wheel 不能替代本次带插桩的构建。两组库不要安装进同一个 venv。

### 3.6 DVM 警告处理

首次 torch-npu 插桩构建在 DVM 中遇到 `-Werror=mismatched-new-delete`。最终对**两组 DVM 编译调用**统一增加 `-Wno-error=mismatched-new-delete`：仍显示这条警告，但不把它当成终止构建的错误，没有全局关闭 `-Werror`。

两组 torch-npu 都归档旧尝试后从纯源码重测。15 个默认 DVM 目标文件在此调整前后的 SHA256 完全一致。构建脚本已包含该处理，不需要手工改 DVM 源码。

## 4. 为什么选 LLD：避免把链接异常算成正常插桩成本

“编译”常被用来泛指整个构建，但实际上最后还有一个链接阶段。最初的异常主要发生在 GNU BFD 2.38 链接 `libtorch_cpu.so` 时：插桩增加大量代码节区和重定位，放大了 AArch64 勘误跳板处理中的遍历成本。

原 BFD 的该链接步骤曾从约 158 秒增加到约 3398 秒；这组诊断与其他探针有重叠，不作为最终性能数据。换 LLD 后相同输入曾在约 36.9 秒完成链接，但“链接返回成功”不代表产物可用。

之后发现旧 LLD 配合 GNU 链接脚本的方案虽然快，却出现 PyTorch 导入 SIGSEGV，因此被否决。最终采用 **LLD 22.1.8 + 原生布局**，保留上游符号排序和 AArch64 勘误修补，再检查实际导入、CPU/NPU 运算、插件采集、源码解析、SQL 和 HTML。

结论不是“任意 LLD 配置都行”，也不是“删掉硬件修补选项”。本次两组必须统一使用已经验证的配置。诊断历史见服务器 `diagnostics/linker`；失败尝试 r3/r4/r5/r6 不混入正式结果。

## 6. 本次插件到底修了什么

### 6.1 30GB 的原因：把重复执行记录当成图来存

旧原生模式为每次函数进入/退出写一条记录，重复循环和模板实例会生成海量事件，再在离线阶段归并。最初 CPU fill 产生约 30GB 原始记录时，已经发生预算溢出，因此那不是“一个 fill 的完整源码图”，也不是可作为最终验证的完整采集。

另外，之前使用插件自动生成的运行时公开 API 目录，并不是用户指定的共享清单；后来按测试缩小 API 范围的实验也不符合需求。最终改成每个测试使用同一份共享清单，记录其中实际触达、能解析的 Python 入口和其后继。

共享清单共 **10,362 项 API：Python 8,559、C++ 1,803，90 类场景**，位于：

```text
R/runtime-scenarios-c03-c05/api-ledger-10362.json
SHA256 c086abe9b812c2c315f1c208dd25b7c83f9d5b0fe825710f25f5fb78d2a0cd48
```

“用完整清单”不表示一次测试会执行一万多个 API，也不表示它们都能被当前运行时解析。清单里的不可调用项、未加载项和不支持解析的项不能声称已观测。C++ 文档条目尚未独立绑定为 API 根，但被插桩的原生后继仍会采集。

### 6.2 采集时就复用路径

新增 `--callchain-native-storage=paths`。它维护当前调用栈，按已有父路径、函数和调用点查找结构，重复经过时只增加计数；各 Python 调用上下文另外记录支持哪些原生路径。不同 API 的分支不会因为共享结构就随意拼在一起。

原生输出是 `native-paths.bin`，不再为每次调用无限追加进入/退出记录。栈溢出、路径或支持记录预算耗尽、不配对退出等都会标记为采集失败/不完整，不会静默当成成功。

这一步仍用运行时地址作为临时采集依据；离线解析后才进一步按源码定义归并。Python 观察记录仍保存在 `events.jsonl`，也不是所有数据都只剩一个计数。

旧 `events` 模式仍保留，而且 CLI 默认值仍是 `events`。要使用本次方案，必须明确传入 `--callchain-native-storage=paths`。

### 6.3 对象复用不会缩短一条路径

源码对象是函数、类等源码定义，不是某次运行的内存地址。例如：

```text
路径：A → B → A → C
路径位置：4 个
唯一源码对象：3 个（两次 A 引用同一份 A）
```

同一对象出现不同后继时，保留实际分支；递归再次进入同一对象时，保留路径层级。真实 C 扩展回归验证中，一个函数递归出现 5 次，紧凑模式与逐事件模式都有 5 个路径位置，但只对应一个源码对象。

数据库中 `entities` 保存对象，`paths` 保存带 API/祖先上下文的路径位置，`canonical_relations` 是去重后的对象关系。全局关系图里的任意走法不能冒充一次实际执行；追踪有证据的链条应使用 API 路径视图。

紧凑模式保留路径、分支和次数，**不保存每次调用的时间戳及先后顺序**。如果需求是重放某一次执行的完整时间线，应另行使用逐事件模式并控制范围。聚合次数保存在采集/重放证据中，不要把 SQL 的路径行数当成调用次数。

### 6.4 源码身份归一化

- Python：运行时 code object 的位置与 AST 定义匹配，别名和实例不另外造一个源码定义；不能唯一匹配的记录保留未解析。
- C++：从匹配 ELF 的函数地址读取 DWARF 声明文件、行、列，再核对源码声明标识符。身份不再包含编译后的 linkage name。
- 同一模板定义的多个实例共用一个源码对象；不同重载、显式特化对应不同源码定义时保持区分。不是简单删掉字符串里的 `<...>`。
- venv 中复制的头文件，只有与仓库文件具有明确路径对应关系且字节完全一致，才复用仓库源码身份。
- 宏生成、缺失坐标或无法验证的对象保留未解析记录。源码版本改变后的身份迁移不靠猜测。

实际观测中，`std::forward` 的 111 个编译实例复用了一份源码定义。运行时长得不同不必然是不同对象；无法证明相同时，也不会强行合并。

### 6.5 另外三处修复

| 问题 | 原因与修改 | 验证 |
| --- | --- | --- |
| libdw 解析 `.gnu_debuglink` 时崩溃 | 补上 `dwfl_standard_find_debuginfo` 回调；与 LLD 产物是否正确是两件事 | 调试文件存在/缺失均有回归 |
| 离线重放反复扫描同一地址的模块映射 | 每个 `Modules` 实例缓存地址解析结果 | 固定证据输出 SHA 相同；CPU clone 2.899→1.742 秒，NPU to 22.098→3.201 秒 |
| 新钩子导致 NPU 初始化 `aclInit 500000` | 初版路径栈放在静态线程局部区，增加约 256KiB TLS；改成开始采集时按需分配，预加载 TLS 降至 180 字节 | 同一最小栈线程程序：旧钩子 `pthread_create=22`，修复后为 0；NPU 采集恢复 |

地址解析缓存是**离线分析加速**，与 PyTorch 编译缓存、运行时间测量不是一回事。NPU 初始化问题也没有通过重启驱动或改变系统安全配置绕过。

对应实现主要在 `catalog.py`、`object_capture.py`、`hooks.c`、`path_capture.h`、`compact.py`、`native.py`、`dwarf_lookup.c`、`source_entities.py` 和 `database.py`。最终 74 项插件回归通过，包括路径等价、分支隔离、重复量级增加时原生文件不增长、预算失败、递归层级、模板/重载身份和小栈线程兼容。

### 7.1 采集一个真实测试

```bash
R=/home/workspace-ycy/compile-performance
D="$R/runtime-scenarios-c03-c05"
source "$R/environment/activate-lld-instrumented.sh"
cd "$D"
export SCENARIO_DEVICE=cpu PYTORCH_TESTING_DEVICE_ONLY_FOR=cpu
export TORCH_DEVICE_BACKEND_AUTOLOAD=0 PYTEST_DISABLE_PLUGIN_AUTOLOAD=1
export OMP_NUM_THREADS=1 MKL_NUM_THREADS=1
unset SCENARIO_API_FILTER

# 必须是不存在的新目录；插件不会覆盖原证据。
CAP="$D/captures-manual/fill-cpu-001"
python -m pytest -p trace_api_chain.pytest_plugin \
  'test_scenario_trace_warm.py::test_selected[C03_fill__cpu]' \
  --callchain-out="$CAP" --callchain-mode=full \
  --callchain-native-storage=paths \
  --callchain-api-catalog="$D/api-ledger-10362.json" \
  --callchain-max-events=10000000 --callchain-max-paths=1000000 \
  --callchain-max-references=1000000 --callchain-timeout=1800
```

测试适配器先执行一次相同方法进行预热，再独立采集一次。已知失败方法也会重跑并保留失败；不修改原方法体来让测试通过。

NPU 运行时，同时把两个 device 环境变量改为 `npu`，并把 nodeid 中的 `__cpu` 改成 `__npu`；某些方法还有 `float32/float64` 后缀，完整 ID 见服务器 `case-manifest-cpu.json` / `case-manifest-npu.json`。不能只改环境变量却仍选 CPU 的 ID。

`--callchain-max-events` 在 paths 模式限制“上下文/路径支持记录数”，不是累计调用次数；`--callchain-max-paths` 限制原生路径节点数。预算是容错上限，不是让采集在达到上限后仍伪装完整。

查看 `capture-result.json`：`status=captured` 且 `gaps=[]` 表示声明范围内没有报告采集缺口。还要单独看 `pytest_exit_code`；测试断言失败和采集失败是不同状态。

### 7.2 离线生成共享数据库

```bash
trace-api-chain replay "$CAP" --db "$D/manual-api-callchains.sqlite" \
```

原生地址与该次采集的 ELF、源码版本必须对应。不要把新编译的库覆盖旧库后，仍拿旧地址直接解释。源码根标签要保持一致，才能让同一来源的对象复用。

同一个 SQLite 可以容纳多个测试和多个 API，不要为每个 API 建一份独立对象库。`--slot` 表示该测试证据的名字，同槽刷新替换该测试的贡献；需要保留多个配置时使用不同槽。重复导入同一证据不会一直复制对象。

## 8. 结果应该怎样读

### 8.1 编译与安装耗时

| 组件 | 默认 | 同时增加两个选项 | 增幅 |
| --- | ---: | ---: | ---: |
| PyTorch | 438.81 秒 | 755.95 秒 | 72.27% |
| torch-npu | 375.61 秒 | 905.82 秒 | 141.16% |
| 分项相加 | 814.42 秒 | 1661.78 秒 | 104.04% |

PyTorch 计时包含配置、代码生成、编译、链接及 pip 构建/安装；后续整理 editable 安装树不计入。torch-npu 计时包含配置、代码生成、编译、链接及 wheel 打包，之后安装 wheel 不计入。合计是分项相加，不是另外测得的一段连续墙钟时间。

检查了全新源码/构建目录、实际 GCC 调用、对象文件时间戳，没有使用 ccache/sccache。两组分别审计到 PyTorch 2,976 次、torch-npu 1,681 次编译器调用，插桩组全部包含两个选项。

但没有清 Linux 页缓存，也没有重启机器；每组只有一次有效构建，且顺序固定。因此可说“没有复用编译产物”，不能说“完全排除了所有缓存影响”，也不能给统计置信区间。详见 [benchmark-report.txt](validation/2026-10-26/benchmark-report.txt) 和 [cache-audit.json](validation/2026-10-26/cache-audit.json)。

## 9. 常见问题如何排查

| 现象 | 先检查什么 |
| --- | --- |
| `import trace_api_chain` 找不到 | 是否加载 `plugin-env.sh`，是否使用正确的 Python |
| `no_compiler_events` | 是否误用了默认库/wheel；是否检查了真实 GCC 命令含插桩选项 |
| 采集目录已存在 | 换一个新目录；原证据不要覆盖 |
| `capture_incomplete` 或非空 gaps | 看预算、配对、线程及钩子错误；不能只凭 pytest 通过就判定采集成功 |
| NPU 初始化 `500000` | 先在无 `LD_PRELOAD` 的同环境做初始化，再区分插件和设备问题；新插件已修复小栈 TLS 问题 |
| 重放崩溃于 debuglink | 核对加载的是带 libdw 回调修复的新插件 |
| 大量 unresolved | 检查构建是否带 `-g1`、源码是否还在、版本是否一致；宏生成/缺失坐标仍可能无法确认 |
| 构建看起来很快 | 核对是不是复用了 build、wheel、成功状态或 `--resume`，以及计时范围是否相同 |
| 链接卡很久 | 核对实际链接器版本和 CMake 原生布局，不能只看命令名称叫 `ld.lld` |
| 改了源码但运行不变 | 打印 `trace_api_chain.__file__`，检查独立运行目录是否刷新 |
