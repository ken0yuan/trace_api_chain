# 模块元数据故障与重复回放的候选修复

此分支为隔离验证候选，未替换正式任务的运行代码。

## 实际故障

两个原始 LSTMCell 用例 `001229-2f370e1cb610`、`001230-e64750d54b29`
重测时 pytest 通过，采集分别运行约 5540.533、5644.625 秒，但均报告
`collector_error:TypeError`。原始事件中的完整错误栈确认：
`Recorder.metadata()` 对语义元数据执行 JSON 编码时遇到实际 module 对象。
CPython 的 C callable 可以将模块对象直接保存在 `__module__`，不能假定该字段恒为字符串。

候选修复保留模块名称，同时记录实际元数据对象身份和显式引用；模块命名空间及新子对象继续展开。
不使用 `repr()` 代替对象，不调用用户自定义字符串转换来掩盖错误。
过去可编码的非常规字面量元数据另存完整 JSON 快照，并保留其实际对象引用。
普通字符串元数据的编码不变。

两例最新回执仍是不完整采集，不因 pytest 通过改为完整。它们的旧有效 current 图摘要
分别仍为 `dc04400ac8e2ec82e1142cba77e0dea2c1acc7d9dc54bd7b95efac3cce7ed05e`
和 `54d4f8515379119dec1e0e8f03a53ee2ee318b3a08012ace1c1582949e006c42`，
与重测前归档回执一致、gaps 为空。失败原始证据和未验证 fork 分支保留。

## 整理阶段的重复工作

37 GiB 原始 LinearCE 输入的独立整理验证仍在运行时，非阻塞栈反复落在
`replay.rebuild()` 对同一大批引用状态逐项查找 parent、校验并构造初始 view。
这不是全库扫描，也不是已经证明的死锁。

候选只在私有文件读入的不可变证据中启用完整初始批次复用。首次仍执行所有检查；
后续仅当 view 为空、无删除项且整个状态 ID 序列精确相同时复用独立映射。
新状态、新后继或非空 view 更新仍完整校验。缓存有限额；公开可变输入默认不启用。
每次调用、对象观察、引用范围和拓扑输出均保留，未减少采集。

## 验证与限制

Windows Python 3.13 的 11 项针对性测试通过；它们使用 Python 遍历后备实现，
包含真实 CPython C callable 的 module 对象元数据，不代表 Linux C 遍历或 NPU 验收。
本地 12000 个 parent、100 次调用的 ABBA 合成对照产生完全相同的完整图 SHA；
其耗时改善只能说明该重复工作的局部因果，不代表原始慢用例已修好。

Linux 首轮候选为 303 trace 通过、1 项失败，API 185 通过、9 项既定跳过。
失败来自既有测试的监测函数未转发新增关键字参数；修复监测函数并加强参数断言后，
在全新候选目录重跑完整回归，保留首轮失败记录。重跑结果为 304 trace 通过（76.05 秒）、
185 API 通过、9 项既定跳过（26.15 秒）。Linux 的实际 C callable 模块对象和新子引用测试通过。

部署前仍需真实冻结证据的完整事件/图/14 表逐行对照、
新采集元数据边界及真实原始用例验收。不能用合成基准或小图证明替代原始大例。
正式采集、现有私有 37 GiB 验证进程和已有数据库均未被此候选改动。
